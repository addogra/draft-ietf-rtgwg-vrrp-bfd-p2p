Abstract

   This document describes how Point-to-Point Bidirectional Forwarding
   Detection (BFD) can be used to support sub-second detection of an
   Active Router failure in the Virtual Router Redundancy Protocol
   (VRRP).  This document updates RFC 9568.

1.  Introduction

   The Virtual Router Redundancy Protocol (VRRP) provides redundant
   Virtual gateways in the Local Area Network (LAN), which is typically
   the first point of failure for end-hosts sending traffic out of the
   LAN.  Fast failure detection of VRRP Active is critical in supporting
   high availability of services and improved Quality of Experience to
   users.  In VRRP [RFC9568] specification, Backup Routers depend on
   VRRP packets generated at a regular interval by the Active Router, to
   detect the health of the VRRP Active.  Faster failure detection can
   be achieved within VRRP protocol by reducing the Advertisement and
   Active Down Interval.  However, sub-second Advert timers, can put
   extra load on CPU and the network bandwidth which may not be



Gupta, et al.           Expires 10 February 2027                [Page 2]

Internet-Draft                  VRRP BFD                     August 2026


   desirable.

   Since the VRRP protocol depends on the availability of Layer 3 IPv4
   or IPv6 connectivity between redundant peers, the VRRP protocol can
   interact with the Layer 3 variant of BFD as described in [RFC5881] to
   achieve a much faster failure detection of the VRRP Active on the
   LAN.  BFD, as specified by the [RFC5880] can provide a much faster
   failure detection in the range of 150ms, if implemented in the part
   of a Network device which scales better than VRRP when sub-second
   Advert timers are used.

   Terminology of this draft has been updated conform to inclusive
   language guidelines for VRRP Inclusive Terminologies [RFC9568].  The
   IETF has designated National Institute of Standards and Technology
   (NIST) "Guidance for NIST Staff on Using Inclusive Language in
   Documentary Standards" [NISTIR8366] for its inclusive language
   guidelines.

2.  Terminology

   This document uses the terminology defined in Section 1.7 of
   [RFC9568].  The following terms are used by this specification:

   Active Router  The VRRP Router currently responsible for forwarding
      packets sent to the IPvX addresses associated with the Virtual
      Router.

   Backup Router  A VRRP Router available to assume forwarding
      responsibility if the current Active Router fails.

   Backup Advertisement  A VRRP packet with Type 2, sent by a Backup
      Router to advertise its presence and priority.

   Peer Table  Per-Virtual-Router state learned from the source
      addresses of Advertisements and Backup Advertisements and used to
      identify VRRP peers.

   Critical Backup  The highest-priority Backup Router, with ties
      resolved using the primary IPvX address as specified in this
      document.

   Critical Path BFD Session  The point-to-point BFD session between the
      current Active Router and the Critical Backup.

   Critical BFD Binding  The association of a Virtual Router instance
      with its current Critical Path BFD Session.

   Eligible BFD Failure  An Up-to-Down transition of the Critical Path

      Backup Router, such a transition is eligible only while the local

4.  Applicability of Point-to-Point BFD

   BFD for IPv4 or IPv6 (Single Hop) [RFC5881] requires that in order
   for a BFD session to be formed both peers participating in a BFD
   session need to know its peer IPv4 or IPv6 address.  This poses a
   unique problem with the definition of the VRRP protocol, that makes
   the use of BFD for IPv4 or IPv6 [RFC5881] more challenging.  In VRRP
   it is only the Active Router that sends Advert packets.  This means
   that an Active Router is not aware of any Backup Routers, and Backup
   Routers are only aware of the Active Router.  This also means that a
   Backup Router is not aware of any other Backup Routers in the
   Network.

   Since BFD for IPv4 or IPv6 [RFC5881] requires that a session be
   formed by both peers using a full destination and source address,
   there needs to be some external means to provide this information to
   BFD on behalf of VRRP.  Once the peer information is available, the
   current Active Router and the selected Critical Backup form the
   Critical Path BFD Session for the Virtual Router.  This mechanism
   does not require a full mesh of BFD sessions among the VRRP Routers.
   An Eligible BFD Failure is interpreted as an Active Down event only
   by the currently selected Critical Backup.  Other Backup Routers
   remain in the Backup state and continue to use the Active_Down_Timer,
   including the Skew_Time procedures specified by [RFC9568].

   NOTE: At all times, the normal fail-over mechanism defined in the
   VRRP [RFC9568] will be unaffected, and the BFD fail-over mechanism
   will always resort to normal VRRP fail-over.

   This document defines the mechanism used by VRRP to build a Peer
   Table, select the Critical Backup, and form the Critical Path BFD
   Session.  An Eligible BFD Failure signals an Active Down event only
   at the current Critical Backup.  This requires an extension to the
   VRRP protocol.

   This can be achieved by defining a new type in the VRRP Advert
   packet, and allowing VRRP peers to build a peer table in any of the
   operational state, Active or Backup.

4.1.  Extension to VRRP protocol

   In this mode of operation, VRRP Routers learn adjacent VRRP Routers.
   All Backup Routers periodically send BACKUP ADVERTISEMENT packets so
   that the participating routers can build the Peer Table and select
   the Critical Backup.  The Active Router continues to send
   ADVERTISEMENT packets as defined by [RFC9568].  Only the current
   Active Router and the selected Critical Backup form the Critical Path
   BFD Session.

   Additionally, Advert packets sent from Backup Peers must not use the
   Virtual router MAC address as the source address.  Instead it must
   use the Interface MAC address as the source address from which the
   packet is sent from.  This is because the source MAC override feature
   is used by the Active to send Advert packets from the Virtual Router
   MAC address, which is used to keep the bridging cache on LAN switches
   and bridging devices refreshed with the destination port for the
   Virtual Router MAC.

4.2.  VRRP Peer Table

   VRRP peers form the Peer Table by learning the source address of the
   enclosing IPv4 or IPv6 packet carrying an ADVERTISEMENT or BACKUP
   ADVERTISEMENT.  For IPv4, this is the sender's primary IPv4 address;
   for IPv6, this is the sender's interface link-local address, as
   specified by [RFC9568].  This learned source address, and not an
   address in the protected IPvX address list, identifies the peer and
   the endpoint of the Critical Path BFD Session.

   A peer entry should be removed from the peer table if Advert is not
   received from a peer for a period of (3 * the Advert interval).

   The type field specifies the type of this VRRP packet.  The type
   field can have two values.  Type 1 (ADVERTISEMENT) is used by the
   VRRP Active Router.  Type 2 (BACKUP ADVERTISEMENT) is used by the
   VRRP Backup Router.  This is to distinguish the packets sent by the
   VRRP Backup Router.  VRRP Backup fills Backup_Advertisement_Interval

   fields are encoded as specified for an ADVERTISEMENT by [RFC9568].

      1 ADVERTISEMENT
      2 BACKUP ADVERTISEMENT

   A packet with unknown type MUST be discarded.

   A BACKUP ADVERTISEMENT MUST carry the Count IPvX Addr and IPvX
   Address(es) fields for the same Virtual Router in the same manner as
   an ADVERTISEMENT.  The minimum Count IPvX Addr is one; a packet with
   a count of zero MUST be ignored.  Receivers MUST apply the applicable
   address-list validation from Section 7.1 of [RFC9568].  The listed
   addresses identify the IPvX addresses protected by the Virtual
   Router; they are not BFD endpoints.  The BFD endpoint is learned from
   the source address of the enclosing IPv4 or IPv6 packet.

   Once the Peer Tables are formed, each router independently selects

   the normal VRRP Active_Down_Timer.

4.5.  Critical BFD session

   Each router selects the Critical Backup from the Backup Routers for
   the Virtual Router, including the local router when it is in the
   Backup state.  The Backup Router with the highest VRRP Priority is
   selected.  If two or more Backup Routers have equal Priority, the one
   with the highest primary IPvX source address is selected using the
   address ordering specified by [RFC9568].  The Critical BFD Session is
   formed only between the current Active Router and this selected
   Critical Backup.

   In the above example, the Critical BFD Session is formed between Rtr1
   and Rtr2.  If that session transitions from Up to Down while Rtr2
   remains the selected Critical Backup, Rtr2 treats the transition as
   an Active Down event, immediately assumes the Active role for VRID 1,
   and sends a Type 1 ADVERTISEMENT.  Rtr3 does not change state in
   response to that BFD transition.  It remains in Backup state and
   continues to use the Active_Down_Timer and Skew_Time procedures in
   [RFC9568].

   A Backup Router MUST map an Up-to-Down transition of the Critical BFD
   Session to an Active Down event only when the local router is the
   currently selected Critical Backup for that Virtual Router.  A Backup
   Router that is not the Critical Backup MUST NOT change its VRRP state
   as a result of that BFD session-state transition.

4.6.  Protocol State Machine

4.6.1.  Parameters Per Virtual Router

   Following parameters are added to the VRRP protocol to support this
   mode of operation.

 Backup_Advertisement_Interval  Time interval between
                                BACKUP ADVERTISEMENTS
                                (centiseconds). Default is 100
                                centiseconds (1 second).

 Backup_Adver_Interval          Advertisement interval contained in
                                BACKUP ADVERTISEMENTS received from
                                the Backup (centiseconds). This
                                value is saved by virtual routers
                                used, to compute Backup_Down_Interval.

 Backup_Down_Interval           Time interval for VRRP instance
                                to declare Backup down
                                (centiseconds). Calculated as
                                (3 * Backup_Adver_Interval) for
                                each VRRP Backup.

 Critical_Backup                The highest-ranked Backup selected using
                                the procedure described in the Critical
                                BFD session section of this document.

 Critical_BFD_Session           The Critical BFD Session is
                                the session between
                                the VRRP Active and Critical_Backup.

 Critical_BFD_Binding           Associates this Virtual Router instance
                                with its current Critical_BFD_Session.

4.6.2.  Timers

   Following timers are added to the VRRP protocol to support this mode
   of operation.

   Backup_Down_Timer          Timer that fires when BACKUP ADVERTISEMENT
                              has not been heard from a backup peer for
                              Backup_Down_Interval.

   Backup_Adver_Timer         Timer that fires to trigger sending of
                              BACKUP ADVERTISEMENT based on
                              Backup_Advertisement_Interval.

5.  Scalability Considerations

   To reduce the number of packets generated at a regular interval,
   Backup Advert packets may be sent at a reduced rate as compared to
   Advert packets sent by the VRRP Active.

6.  Operational Considerations

   A VRRP peer that forms a member of this Virtual Router, but does not
   support this feature or extension must be configured with the lowest
   priority, and will only operate as the Router of last resort on
   failure of all other VRRP routers supporting this functionality.



Gupta, et al.           Expires 10 February 2027               [Page 19]

Internet-Draft                  VRRP BFD                     August 2026


   The mechanism defined by this document is intended for deployments
   where BFD can provide a shorter and operationally reliable failure-
   detection time than the VRRP Active_Down_Timer, and where the
   monitored BFD path shares the intended fate with the protected
   forwarding path.  If BFD cannot provide a detection-time advantage,
   the integration provides no convergence benefit while adding BFD
   session state, periodic control traffic, configuration, and another
   operational dependency.  In that case, native VRRP failure detection
   should be used without this integration.

   BFD reports reachability of the monitored bidirectional path; it does
   not by itself determine the health of the remote VRRP process.
   Therefore, BFD supplements rather than replaces VRRP Advertisements
   and the Active_Down_Timer.  Operators should ensure that filters,
   policers, shapers, and queueing do not disrupt BFD packet delivery
   relative to the configured BFD Detection Time.

   The operational issues described in Section 8 of [RFC9568] continue
   to apply.  The operational considerations described in Section 7 of
   [RFC5880], including packet treatment, processing load, and the
   trade-off between protocol overhead and failure-detection time, also
   apply to this mechanism.  Implementations and operators should also
   follow the generic BFD application guidance in [RFC5882],
   particularly its description of BFD as an advisory service to client
   protocols.

   This Draft does not preclude the possibility of the peer table being
   populated by means of manual configuration, instead of using the
   BACKUP ADVERTISEMENT as defined by the Draft.

7.  Applicability to VRRPv2

   The workings of this Draft can be extended to VRRPv2 defined in
   RFC3768, with the introduction of BACKUP ADVERTISEMENT and Peer
   Table as outlined in the Draft.
