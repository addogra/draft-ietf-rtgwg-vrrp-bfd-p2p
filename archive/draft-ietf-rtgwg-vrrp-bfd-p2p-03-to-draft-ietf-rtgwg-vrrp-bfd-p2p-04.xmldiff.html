82      <name>Introduction</name>
83      <t>
84The Virtual Router Redundancy Protocol (VRRP) provides redundant Virtual gateways in the Local Area Network (LAN), which is typically the first point of failure for end-hosts sending traffic out of the LAN. Fast failure detection of VRRP Active is critical in supporting high availability of services and improved Quality of Experience to users. 
85
86In VRRP <xref target="RFC9568"/> specification, Backup routers depend on VRRP packets generated at a regular interval by the Active router, to detect the health of the VRRP Active. Faster failure detection can be achieved within VRRP protocol by reducing the Advertisement and Active Down Interval. However, sub second Advert timers, can put extra load on CPU and the network bandwidth which may not be desirable. 
87</t>
88      <t>Since the VRRP protocol depends on the availability of Layer 3 IPv4 or IPv6 connectivity between redundant peers, the VRRP protocol can interact with the Layer 3 variant of BFD as described in <xref target="RFC5881"/> to achieve a much faster failure detection of the VRRP Active on the LAN. BFD, as specified by the <xref target="RFC5880"/> can provide a much faster failure detection in the range of 150ms, if implemented in the part of a Network device which scales better than VRRP when sub second Advert timers are used. 
89</t>

101      <name>Applicability of Point to Point BFD</name>
102      <t>BFD for IPv4 or IPv6 (Single Hop) <xref target="RFC5881"/> requires that in order for a BFD session to be formed both peers participating in a BFD session need to know its peer IPv4 or IPV6 address. This poses a unique problem with the definition of the VRRP protocol, that makes the use of BFD for IPv4 or IPv6 <xref target="RFC5881"/> more challenging. In VRRP it is only the Active router that sends Advert packets. This means that a Active router is not aware of any Backup routers, and Backup routers are only aware of the Active router. This also means that a Backup router is not aware of any other Backup routers in the Network.
103</t>
104      <t>Since BFD for IPv4 or IPv6 <xref target="RFC5881"/> requires that a session be formed by both peers using a full destination and source address, there needs to be some external means to provide this information to BFD on behalf of VRRP. Once the peer information is made available, VRRP can form BFD sessions with its peer Virtual Router. The BFD session for a given Virtual Router is identified as the Critical Path BFD Session, which is the session that forms between the current VRRP Active router, and the highest priority Backup router. When the Critical Path BFD Session identified by VRRP as having changed state from Up to Down, then this will be interpreted by the VRRP state machine on the highest priority Backup router as a Active Down event. A Active Down event means that the highest priority Backup peer will immediately become the new Active for the Virtual Router.</t>
105      <t>NOTE: At all times, the normal fail-over mechanism defined in the VRRP  <xref target="RFC9568"/> will be unaffected, and the BFD fail-over mechanism will always resort to normal VRRP fail-over.
106</t>
107      <t>This draft defines the mechanism used by the VRRP protocol to build a peer table that will help in forming of BFD session and the detection of Critical Path BFD session. If the Critical Path BFD session were to go down, it will signal a Active Down event and make the most preferred Backup router as the VRRP Active router. This requires an extension to the VRRP protocol.
108</t>
109      <t>
110This can be achieved by defining a new type in the VRRP Advert packet, and allowing VRRP peers to build a peer table in any of the operational state, Active or Backup.
111</t>
112      <section>
113        <name>Extension to VRRP protocol</name>
114        <t>
115In this mode of operation VRRP peers learn the adjacent routers, and form BFD session between the learnt routers. In order to build the peer table, all routers send VRRP Advert packets whilst in any of the operational states (Active or Backup). Normally VRRP peers only send Advert packets whilst in the Active state, however in this mode VRRP Backup peers will also send Advert packets with the type field set to BACKUP ADVERTISEMENT type defined in <xref target="format"/> of this document. The VRRP Active router will still continue to send packets with the Advert type as ADVERTISEMENT as defined in the VRRP protocol. This is to maintain inter-operability with peers complying to VRRP protocol.</t>
116        <t>
117Additionally, Advert packets sent from Backup Peers must not use the Virtual router MAC address as the source address. Instead it must use the Interface MAC address as the source address from which the packet is sent from. This is because the source MAC override feature is used by the Active to send Advert packets from the Virtual Router MAC address, which is used to keep the bridging cache on LAN switches and bridging devices refreshed with the destination port for the Virtual Router MAC.</t>
118      </section>

122VRRP peers can now form the peer table by learning the source address in the ADVERTISEMENT or BACKUP ADVERTISEMENT packet sent by VRRP Active or Backup peers. This allows peers to create BFD sessions with other operational peers.
123</t>

125A peer entry should be removed from the peer table if Advert is not
126received from a peer for a period of (3 * the Advert interval).

        • <t>
          • The Virtual Router Redundancy Protocol (VRRP) provides redundant Virtual gateways in the Local Area Network (LAN), which is typically the first point of failure for end-hosts sending traffic out of the LAN. Fast failure detection of VRRP Active is critical in supporting high availability of services and improved Quality of Experience to users. In VRRP <xref target="RFC9568"/> specification, Backup routers Routers depend on VRRP packets generated at a regular interval by the Active router, Router, to detect the health of the VRRP Active. Faster failure detection can be achieved within VRRP protocol by reducing the Advertisement and Active Down Interval. However, sub second sub-second Advert timers, can put extra load on CPU and the network bandwidth which may not be desirable.
          • </t>
        • <t>
          • Since the VRRP protocol depends on the availability of Layer 3 IPv4 or IPv6 connectivity between redundant peers, the VRRP protocol can interact with the Layer 3 variant of BFD as described in <xref target="RFC5881"/> to achieve a much faster failure detection of the VRRP Active on the LAN. BFD, as specified by the <xref target="RFC5880"/> can provide a much faster failure detection in the range of 150ms, if implemented in the part of a Network device which scales better than VRRP when sub second sub-second Advert timers are used.

82      <name>Introduction</name>
83      <t>
84The Virtual Router Redundancy Protocol (VRRP) provides redundant Virtual gateways in the Local Area Network (LAN), which is typically the first point of failure for end-hosts sending traffic out of the LAN. Fast failure detection of VRRP Active is critical in supporting high availability of services and improved Quality of Experience to users. 
85
86In VRRP <xref target="RFC9568"/> specification, Backup Routers depend on VRRP packets generated at a regular interval by the Active Router, to detect the health of the VRRP Active. Faster failure detection can be achieved within VRRP protocol by reducing the Advertisement and Active Down Interval. However, sub-second Advert timers, can put extra load on CPU and the network bandwidth which may not be desirable. 
87</t>
88      <t>Since the VRRP protocol depends on the availability of Layer 3 IPv4 or IPv6 connectivity between redundant peers, the VRRP protocol can interact with the Layer 3 variant of BFD as described in <xref target="RFC5881"/> to achieve a much faster failure detection of the VRRP Active on the LAN. BFD, as specified by the <xref target="RFC5880"/> can provide a much faster failure detection in the range of 150ms, if implemented in the part of a Network device which scales better than VRRP when sub-second Advert timers are used. 
89</t>

135      <name>Applicability of Point-to-Point BFD</name>
136      <t>BFD for IPv4 or IPv6 (Single Hop) <xref target="RFC5881"/> requires that in order for a BFD session to be formed both peers participating in a BFD session need to know its peer IPv4 or IPv6 address. This poses a unique problem with the definition of the VRRP protocol, that makes the use of BFD for IPv4 or IPv6 <xref target="RFC5881"/> more challenging. In VRRP it is only the Active Router that sends Advert packets. This means that an Active Router is not aware of any Backup Routers, and Backup Routers are only aware of the Active Router. This also means that a Backup Router is not aware of any other Backup Routers in the Network.
137</t>
138      <t>Since BFD for IPv4 or IPv6 <xref target="RFC5881"/> requires that a session be formed by both peers using a full destination and source address, there needs to be some external means to provide this information to BFD on behalf of VRRP. Once the peer information is available, the current Active Router and the selected Critical Backup form the Critical Path BFD Session for the Virtual Router. This mechanism does not require a full mesh of BFD sessions among the VRRP Routers. An Eligible BFD Failure is interpreted as an Active Down event only by the currently selected Critical Backup. Other Backup Routers remain in the Backup state and continue to use the Active_Down_Timer, including the Skew_Time procedures specified by <xref target="RFC9568"/>.</t>
139      <t>NOTE: At all times, the normal fail-over mechanism defined in the VRRP  <xref target="RFC9568"/> will be unaffected, and the BFD fail-over mechanism will always resort to normal VRRP fail-over.
140</t>
141      <t>This document defines the mechanism used by VRRP to build a Peer Table, select the Critical Backup, and form the Critical Path BFD Session. An Eligible BFD Failure signals an Active Down event only at the current Critical Backup. This requires an extension to the VRRP protocol.
142</t>
143      <t>
144This can be achieved by defining a new type in the VRRP Advert packet, and allowing VRRP peers to build a peer table in any of the operational state, Active or Backup.
145</t>

148        <t>

801      <name>Operational Considerations</name>
802      <t>
803A VRRP peer that forms a member of this Virtual Router, but does not support this feature or extension
804must be configured with the lowest priority, and will only operate as the Router of last resort on failure of all other VRRP routers supporting this functionality.
805</t>
806      <t>
807The mechanism defined by this document is intended for deployments where BFD can provide a shorter and operationally reliable failure-detection time than the VRRP Active_Down_Timer, and where the monitored BFD path shares the intended fate with the protected forwarding path. If BFD cannot provide a detection-time advantage, the integration provides no convergence benefit while adding BFD session state, periodic control traffic, configuration, and another operational dependency. In that case, native VRRP failure detection should be used without this integration.
808</t>
809      <t>
810BFD reports reachability of the monitored bidirectional path; it does not by itself determine the health of the remote VRRP process. Therefore, BFD supplements rather than replaces VRRP Advertisements and the Active_Down_Timer. Operators should ensure that filters, policers, shapers, and queueing do not disrupt BFD packet delivery relative to the configured BFD Detection Time.
811</t>
812      <t>
813The operational issues described in Section 8 of <xref target="RFC9568"/> continue to apply. The operational considerations described in Section 7 of <xref target="RFC5880"/>, including packet treatment, processing load, and the trade-off between protocol overhead and failure-detection time, also apply to this mechanism. Implementations and operators should also follow the generic BFD application guidance in <xref target="RFC5882"/>, particularly its description of BFD as an advisory service to client protocols.

971            <abstract>
972              <t>
973 This memo defines the Virtual Router Redundancy Protocol (VRRP) for
974   IPv4 and IPv6.  It is version three (3) of the protocol, and it is
975   based on VRRP (version 2) for IPv4 that is defined in RFC 3768 and in
976   "Virtual Router Redundancy Protocol for IPv6".  VRRP specifies an
977   election protocol that dynamically assigns responsibility for a
978   virtual router to one of the VRRP routers on a LAN.  The VRRP router
979   controlling the IPv4 or IPv6 address(es) associated with a virtual
980   router is called the Active, and it forwards packets sent to these
981   IPv4 or IPv6 addresses.  VRRP Active Routers are configured with
982   virtual IPv4 or IPv6 addresses, and VRRP Backup Routers infer the
983   address family of the virtual addresses being carried based on the
984   transport protocol.  Within a VRRP router, the virtual routers in
985   each of the IPv4 and IPv6 address families are a domain unto
986   themselves and do not overlap.  The election process provides dynamic
987   failover in the forwarding responsibility should the Active become
988   unavailable.  For IPv4, the advantage gained from using VRRP is a
989   higher-availability default path without requiring configuration of
990   dynamic routing or router discovery protocols on every end-host.  For
991   IPv6, the advantage gained from using VRRP for IPv6 is a quicker
992   switchover to Backup Routers than can be obtained with standard IPv6
993   Neighbor Discovery mechanisms.</t>
